# 05 · 「判定完成」早于媒体播完导致误停（推进方式不变）

Status: done

## 背景

用户报障：跑该课程时脚本停在这条文案上，并附现场：

```
章节树说本节点还有未完成，脚本扫遍全部卡片却一个未完成任务点都没看到 —— 判定不可信（多半是任务点的容器变了），已停下
本卡片 1/1 | 后面还有 18 个任务点未完成（含 PPT） | 1324/1482s | 还剩 158s
```

他的判断（原话）：「可能是播放完成状态早于进度条，切换课程时候导致的」。

排查走 `/grill-with-docs`：先在真机上把这条复现并定位（`issues/04` 的「真机只读确认只跳一次」那次没有覆盖「播完 → 自动跳走」这一段，正是漏在这里）。

## 复现与根因（2026-09-30 真机）

选定节点进页面后由脚本自行推进；盯住「容器 `ans-job-finished` / 章节树 `jobUnfinishCount` / 状态条」三者的先后：

| 时刻 | 任务点 | 媒体 | 当前节点树上计数 | 状态条 |
|---|---|---|---|---|
| 09:31:07 | `RAW` 未完成 | 434/490 | `1` | 正在运行 |
| **09:31:10** | **`FIN` 判定完成** | **437/490（还剩 53 秒）** | **仍是 `1`** | **已停下 · treeUnfinishedNotFound** |
| 09:31:16 | `FIN` | 443/490（仍在播） | `NO-EL` 计数消失 | 保持停止 |
| 09:32:18 | `FIN` | 490/490 END → 平台自己 pause | `NO-EL` | 保持停止 |

网络侧同一时间线：`multimedia/log?playingTime=435`（触发完成判定）→ 紧跟一次 `studentstudycourselist?…&chapterId=<当前节点>`。三条事实见 `docs/sites/xuexitong.md`（已就地更正两条旧措辞）。

根因是三条都合法的判断叠在一起：

1. 第 8b 步（`playable.length === 0 && !media.ended`）**当场**离开节点；
2. 卡片账本在「本卡片有可播单元」时被清空，所以「看到过未完成任务点」从来没在播放期间攒下来，等到没有可播单元那一刻才重新记 —— 而刚播完那个已经不算未完成了 → `sawUnfinished = false`；
3. 安全网据此判「解释不清」→ `stop(treeUnfinishedNotFound)`。

**对照**：同一门课另外三条视频的完成比例是 `rt=1`（`241/242`、`232/232`、`308/308` 才 FIN），脚本走「播完 → 等 15 秒 → 跳」那条路，树早已刷新完，一次都没停。所以只要完成比例 < 100% 就必现。

## 范围

改 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`；决定落 `docs/adr/0011`，`0010` 在「一个未完成任务点都没看到 → 停下」那一句就地指路。**不改推进方式**（仍是「从章节树只向前跳到下一个未完成节点」），`0010` 那张安全网仍在，只从「一票否决」改成「复查后再否决」。

两条改动（用户逐条确认，Q4=C / Q5=A）：

- **第 8b 步收窄**：只有媒体**没在播**（暂停 / 已结束 / 加载失败）时才提前离开；正在播就让它播到 `ended`，走既有的「播完固定等一段」。
- **安全网加复查窗口**：新常量 `TREE_RECHECK_GRACE_MS = 15000`、新等待 `PENDING.TREE_UNFINISHED_MISMATCH`、新记忆 `treeMismatch = { nodeId, since }`（跳节点时清掉）；到期仍不一致才 `stop(treeUnfinishedNotFound)`，文案加「又等了 15 秒复查仍是如此」。

## 真机验收记录（2026-09-30）

装新版后核对功能标记：`typeof CONSTANTS.TREE_RECHECK_GRACE_MS` → `"number"`（第八轮），`ACTION.JUMP_NODE` → `"jumpNode"`（第七轮）。

**① 自然路径**：从已完成节点 4.6 进场 → 脚本**只跳一次**到 5.4（中间 5.1–5.3 已完成，一个都没访问）→ 起播 5.4 的 288 秒视频，状态条 `正在运行　本卡片 0/1　|　后面还有 11 个任务点未完成（含 PPT）　|　32/288s　|　还剩 255s`。

**② 故障注入**（把用户在野遇到的那个窗口造出来，DOM 输入与真实一致，只用手工替代「平台刷新章节树」这一步）：

| 步骤 | 动作 | 结果 |
|---|---|---|
| T0 | 采样 | `cur=5.4 cnt=1 fin=0`，正在播 32/288s |
| T1 | 给容器加上 `ans-job-finished` + 暂停媒体 | `{marked:1, paused:true}` |
| T2（+2 秒） | 采样 | **没有停**：`本卡片 1/1 … | 再等 15 秒复查章节树（仍不一致就停下）` |
| T3（+5 秒） | 采样 | 同一句，倒计时 11 秒（窗口在走） |
| T4 | **模拟平台刷新**：去掉当前节点的 `jobUnfinishCount` | `{removed:1}` |
| T5（+2 秒） | 采样 | **正常跳到 5.5**（`cur=cur1236752495`），没有停 |
| T6（+5 秒） | 采样 | 已起播 5.5 的 412 秒视频（3/412s） |
| U1 | 在 5.5 上只注入 `ans-job-finished`、**不**暂停媒体 | `{marked:1}` |
| U2/U3 | 采样 | `cur` 仍是 5.5、媒体 19→24/412s 继续走、**没有跳走也没有进入复查窗口** |

对照旧行为：T2 那一刻会直接 `stop(treeUnfinishedNotFound)`（就是用户看到的那条）；U2 那一刻会当场离开节点。

**⚠️ 一条异常观察，如实记（未定论）**：U3 之后约一分钟，清理注入时发现假类已随 DOM 消失，终态是 `cur=5.4`、5.4 那条 288 秒的媒体停在 35/288s —— 页面**回到了 5.4**。合理解释只有一种：平台自己重发了 `studentstudycourselist`，而那次刷新把 `posCatalog_active` 放到了 5.4 之前的位置（或重排），于是「当前节点之后第一个未完成节点」算出来又是 5.4；而 5.4 确实还没做完，跳回去并不算做错事。**但本次会话里我手工删过树上 5.4 的一个计数元素**，无法排除是这个动作引起的连锁，所以只当观察记下、不进 `docs/sites`。若再遇到，先看那一刻 `posCatalog_active` 到底指着谁。

**消耗与副作用（如实记）**：真机期间播到过 4.6 的尾部、5.4 播到约 35 秒、5.5 播到约 25 秒（都是真实播放）；**另外两处是为了造现场**：T1 把 5.4 的媒体 `pause()` 了一次（模拟平台的失焦暂停），并给容器手动加过 `ans-job-finished` 类（纯 DOM、不影响平台记录，结束时已撤掉）。没有改过 `currentTime`、没有碰过任何上报字段、没有代为确认过任何确认框。

## 明确不做

- 不删「点下一节 + 确认框」那条回退路径（用户确认保留）。
- 不复用 `ADVANCE_DELAY_MS` 当复查窗口（手册明确允许用户把它调到 5 秒，共用会让这个修复被一次正常调参调坏）。
- 不用「记一笔刚刚看到过完成」代替复查窗口（会削弱安全网，理由见 `0011` 的 Considered Options）。
- 不追 `faceCaptureCourse` 那次未复现的误触发（用户定：先放着；线索已记在 `docs/sites/xuexitong.md`）。
