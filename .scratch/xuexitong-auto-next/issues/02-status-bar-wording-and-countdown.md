# 02 · 状态条：文案定稿 + 等待倒计时

Status: done

## 背景

第四轮真机验收后留下四条文案问题（`spec.md` 的 Comments 第四轮末尾），另有一条在 grilling 里被用户升级成新需求：状态条上**看不出脚本是「正在跳过」还是「卡住了」**，要求「给所有等待操作都加一个倒计时，提高反馈」。

本轮决定（全部经用户逐条确认，见 `spec.md` 的 Comments 第五轮）：

- 停止按钮**不碰媒体**——`docs/adr/0008`（因此本轮**没有**与「停止」相关的代码改动）
- 文案里的时限**由常量拼**，不再手写数字
- 倒计时挂在决策核心的记忆上（**唯一来源**），适配层只负责渲染
- 「等待」与停止原因同等对待：**可枚举 + 每个 kind 一条用例**

## 范围

改 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`。**不新增停止原因、不改动作集、不改三层边界**；`CONTEXT.md` 不动（它是站点领域词表，「停止/继续」的语义记在 `0008`）。

### 第 1 步 · 文案定稿（数字由常量拼）

| 字段 | 文案 |
|---|---|
| `courseCompleted` | 没有「下一节」入口了，脚本结束 —— 若后面还有内容，多半是页面结构变了 |
| `mediaLoadFailed` | 视频/音频加载失败，已停下 |
| `mediaNotFound` | 一直没找到可播的视频/音频元素，等了 `${UNREADY_TIMEOUT_MS/1000}` 秒也没有，已停下 —— 可能是任务点结构变了，或卡片层认不出来 |
| `stalled` | 播放卡住了（进度 `${STALL_TIMEOUT_MS/1000}` 秒不前进），已停下 |
| `playbackRefused` | 浏览器拒绝了自动播放（请求起播后 `${START_GIVEUP_MS/1000}` 秒仍没动），已停下 —— 请手动点一下播放 |

- `courseCompleted` 的旧文案是「整门课已跑完」，名不副实：脚本只知道**页面上找不到可见的「下一节」入口**，那也可能是页面没渲染完或站点改版。新文案不再宣称成绩。
- `REASON_TEXT` 的值必须真的读常量（改成函数或模板都行）——否则这一条等于没改。
- `progressText()` 里的 `本卡片无任务点` **保留不动**：「是跳过还是卡住」由第 2 步的倒计时回答，不再另改这段文字。

### 第 2 步 · 等待倒计时

- **决策核心登记** `memory.pending = { kind, dueAt }`，`dueAt` 是绝对时刻；不再等待时清 `null`。**文案不进决策核心**，它只知道可枚举的 `kind`。
- `PENDING` 可枚举，7 个 kind —— 覆盖决策核心里全部的「等待」：

  | kind | 等待什么 | 常量 | 到期 |
  |---|---|---|---|
  | `EMPTY_CARD` | 本卡片 0 个任务点，等它渲染出来 | `EMPTY_CARD_GRACE_MS` | 动手：跳过本卡片 |
  | `ADVANCE_DELAY` | 媒体播完后的固定延迟 | `ADVANCE_DELAY_MS` | 动手：继续推进 |
  | `ADVANCE_COOLDOWN` | 刚推进过（页面没变时更长） | `ACTION_COOLDOWN_MS` / `ADVANCE_REPEAT_GUARD_MS` | 动手：重试推进 |
  | `UNREADY` | 等页面交出可播单元 | `UNREADY_TIMEOUT_MS` | 停下：`mediaNotFound` |
  | `START_GIVEUP` | 已请求起播但一直没动 | `START_GIVEUP_MS` | 停下：`playbackRefused` |
  | `PAUSED` | 已起播的媒体被暂停 | `PAUSE_GRACE_MS` | 停下：`focusLostPause` / `manualPause` |
  | `STALLED` | 在播但进度不前进 | `STALL_TIMEOUT_MS` | 停下：`stalled` |

  （适配层的 `TASK_POINT_CACHE_MS` 是 DOM 重扫间隔，用户看不见，**不算**。原本还打算给「定位/切卡片」的冷却单开一个 kind，实现时发现它**永远与 `UNREADY` 并存**（两处都在 `waitForPlayable` 里），只显示一条的规则下它出不来——于是不单开，报 `UNREADY` 那条更有用的。）
- **驱动循环**把记忆交给状态条：`progressText(memory)`（适配层接口第一次出现记忆入参，如实记这条代价）；取的是**判定之后**的记忆，所以倒计时不会慢一拍。渲染规则：
  - 一个 tick 里只登记一条（决策核心保证）；两个倒计时并存时**「放弃类」优先于「重试类」**——会停下的那条决定用户要不要介入，比「多久后重试定位」要紧。⚠️ 这条与 grilling 时说的「最先到期」不同：先到期的那条在 `waitForPlayable` 里几乎总是冷却（4 秒 < 30 秒），会把「再等 N 秒就停下」永久盖住。
  - 剩余时间 `Math.ceil(remaining / 1000)`，下限 0；状态条本身就是 1 秒一刷
  - **停下之后的文案不带等待倒计时**（`还剩 Ns` 是媒体自己的信息，保留）；没有 pending 的等待（在播、什么都不做）也不显示
  - 「还剩 `${剩余}`s」由 `media.currentTime` / `duration` 直接算，**不占** pending
- 措辞：两类必须一眼分得开 —— **动手说「`N 秒后…`」，放弃说「`再等 N 秒…`」**，动词与既有停止原因文案保持一致：

  | kind | 文案 |
  |---|---|
  | `EMPTY_CARD` | `N 秒后跳过本卡片` |
  | `ADVANCE_DELAY` | `N 秒后继续推进` |
  | `ADVANCE_COOLDOWN` | `N 秒后重试推进` |
  | `UNREADY` | `再等 N 秒没动静就停下` |
  | `START_GIVEUP` | `再等 N 秒仍未开始播放　将判定被拒绝` |
  | `PAUSED` | `再等 N 秒仍暂停　将停下` |
  | `STALLED` | `再等 N 秒没进度就停下` |

  ⚠️ 与 grilling 时口头示例的一处差异：`ADVANCE_DELAY` 到期**未必换节**（本卡片还有可播任务点时是就地推进到下一个任务点），所以写「继续推进」而不是「推进到下一节」。

### 第 3 步 · 用例

- `PENDING` **每个 kind 至少一条用例**，在用例文件末尾加自检（与既有的「每条停止原因都必须有用例」同款）。理由：漏掉某个分支的倒计时，症状**和用户抱怨的那个症状一模一样**（看不出在干什么），只有自检能拦住。
- 用例 55 → **57** 条。四个 kind（`EMPTY_CARD` / `ADVANCE_DELAY` / `ADVANCE_COOLDOWN` / `PAUSED` / `START_GIVEUP`）**直接标注在已经存在的等待用例上**——它们本来就在测同一次等待，另起一条只会重复构造；真正新增的是 `UNREADY` 与 `STALLED` 两条，外加一条「正常播放时报 `pending: null`」。
- 断言的是决策核心返回的 `memory.pending`（`kind` 与 `dueAt`，到期时刻也算出来比），不碰渲染。

### 实现时如实记的三处偏差

1. **`START` 不再走冷却**：`throttledAction(ACTION.START, …, 0)`。原来那条 4 秒冷却会**吞掉起播请求**——`startRequestedKey` 在冷却判定之前就被记下了，冷却一旦返回 `WAIT`，之后这个媒体再也不会被请求起播（只能等 6 秒后判 `playbackRefused`）。同一个媒体只请求一次已由 `startRequestedKey` 守住，冷却本来就不需要，顺手修掉。
2. **`STALLED` 只在「本 tick 的 `currentTime` 与上次采样一样」时报**，不是只要在播就报。因为正常播放时 `sample.at` 每 tick 都会被重置，一直报的话会显示成一条恒定的「再等 20 秒没进度就停下」，把「还剩 Ns」挤掉，而且看着吓人。判据就是「进度真的没动」，不需要新阈值。
3. **并存时「放弃类」优先**（见第 2 步）。

## 验收

```bash
node src/tests/decision.test.js        # 全绿 + 两个自检都过
```

真机（`playwright-cli -s=xuexitong`，**仓库根目录**执行，**只留一个章节标签页**）：

1. 装新版（`http://127.0.0.1:8123/src/xuexitong-auto-next.user.js`；首开可能不弹安装页，`reload` 一次）
2. 在 `2.3` 上看：`还剩 Ns` 在跳、推进时出现 `N 秒后继续推进`
3. 三条**还没被触发过**的路径：本卡片没有可播单元 → 切下一张卡片；只剩 PPT → `confirmAdvance`；只剩认不出类型的任务点 → `confirmAdvance`
4. 复验旧事实：真 PPT 任务点的 `jobid` 是写在模块 iframe 属性上还是只在 `data` JSON 里（**找不到纯 PPT 节点就在含视频的卡片里验**，`jobIdOf()` 是两处都读，不依赖「只剩」）

判定标准：倒计时按秒递减、且到期后**确实发生对应的动作或停下**（不是递减完什么也不做）；「停止」的行为与 `docs/adr/0008` 一致（脚本撤出、媒体继续播）。

⚠️ 用户明确表示**不怕留下跳过痕迹**，所以第 4 步不必回避；但装新版要 `reload`，会中断正在播的那个视频。

## 明确不做

- 不给「停止」加暂停媒体（`docs/adr/0008`）。
- 不给 `progressText()` 之外再开任何记忆入参，也不让适配层自己重算时限（那就是把 7 个常量抄第二份）。
- 不引入构建工具链 / 包管理器 / 测试运行器。

**还没验到的四条（如实记，缺样本）**：

1. `ADVANCE_DELAY`：真机上看不到，原因见下——**顺带发现的一处既有行为**：`findMedia()` 给「已播完」的元素 +2 分，所以本卡片还有别的未完成任务点时，一条媒体播完后脚本当场就会选中下一个媒体并 `START`，`media.ended` 那一支轮不到。「播完固定等 15 秒」实际只在**本卡片最后一个可播任务点**播完时才走到。**不是本工单引入的**，要不要改另行决定。
2. `START_GIVEUP`：需要浏览器拒绝自动播放，本机放行，造不出来。
3. `STALLED`：需要真的卡一次，没等到。
4. **两种 `confirmAdvance`（只剩 PPT / 只剩认不出类型）与 PPT `jobid` 复验**：本课程没找到真 PPT 任务点（`pdf` 模块），认不出类型的模块也没出现过。要确认这门课是否根本没有，得把 18 个 Unit 节点只读扫一遍（十几分钟、会真的播放），**等用户点头**。
