# 03 · 两段续播阶梯：暂停 / 被拒后自动续播

Status: done

## 背景

`docs/adr/0002` 明确否掉过「失焦暂停后静默自动续播」，这成了脚本的一条硬边界：光标离开窗口 → 播放器暂停 → 脚本等 5 秒 → 停下 `focusLostPause` / `manualPause`，要人回来点「继续」。而 `docs/sites/xuexitong.md` 的探查证明**这个暂停是播放器元素上一次性的 `mouseout`**（不轮询、回窗口不自动恢复）——**脚本 `play()` 一次就能顶住**。

用户判断这个暂停**不是平台的需求**（项目本身不要求「离开就暂停」，是前端开发人员失误加进来的；本脚本是临时处理方案），要求：暂停后、或脚本自动停止后，**自动尝试续播 5 次、间隔 5 秒**；5 次失败后**停止脚本、再开始一次脚本、再尝试 3 次**。

设计经三轮 grilling 逐条确认，全部决定见 `spec.md` 的 Comments 第六轮与 `docs/adr/0009`。

## 范围

改 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`。反转 `0002` 的第二条被否选项、落新 ADR `0009`。**不改三层边界、不改适配层接口**（续播用的就是「继续」按钮那一个动作）；`CONTEXT.md` 不动（「停止 / 继续 / 续播」的语义归 ADR）。

### 第 1 步 · 阶梯的总体形状

适用**四档**：`focusLostPause`、`manualPause`、`playbackRefused`、`mediaLoadFailed`。**用户按「停止」永不自动续播**。

| 时刻（从「发现异常」起算） | 阶段 | 做什么 | 状态条 |
|---|---|---|---|
| 0s | 一 | 记下起点，排第 1 次 | `5 秒后自动续播（第 1/5 次）` |
| 5 / 10 / 15 / 20 / 25s | 一 | 第 1–5 次：对当前媒体再按一次播放 | `N 秒后自动续播（第 k/5 次）` |
| 25–30s | 一 | 等第 5 次的结果 | `再等 N 秒仍没恢复就重启脚本` |
| **30s** | — | **重启脚本**（重置全部时间基准 + 再播一次） | `脚本已重启　5 秒后自动续播（第 1/3 次）` |
| 35 / 40 / 45s | 二 | 第 1–3 次 | `脚本已重启　N 秒后自动续播（第 k/3 次）` |
| 45–50s | 二 | 等第 3 次的结果 | `再等 N 秒仍没恢复就停下` |
| **50s** | — | **真正停下** | `<原原因> —— 已自动续播 5 次、重启后 3 次均未成功` |

- 「重启后尝试三次」按用户原话理解为**重启之外再三次**，所以二次阶梯在 35/40/45 秒，总窗口 **50 秒**。
- 四档的**第一次尝试统一在 5 秒后**发出 —— 包括原先「立刻停」的 `mediaLoadFailed`。全脚本只有一套时钟、一套文案。
- **重启只发生一次**：二次阶梯用尽后必须由人（或「继续」）解开。

### 第 2 步 · 决策核心

- **新动作** `ACTION.AUTO_RESUME`：语义 = 「对当前媒体再按一次播放」。刻意不复用 `START`（后者只服务 `currentTime === 0` 的起播、且要记 `startRequestedKey`）。适配层 `perform` 里转到 `playOnce()`。
- **新记忆** `resume = { key, stage, attempts, dueAt, playingSince }`；**退休 `pausedSince`**（它的两个用途——暂停宽限、起播判定——都被阶梯的 `dueAt` 接管）。
- **新常量**：`RESUME_INTERVAL_MS = 5000`、`RESUME_MAX_ATTEMPTS = 5`、`RESTART_MAX_ATTEMPTS = 3`。
- **退休常量**：`PAUSE_GRACE_MS`、`START_GIVEUP_MS`（用例里对它们的引用一并改写）。
- **四个调度点**：
  1. `media.failed` → 阶梯（原先是立刻 `stop(MEDIA_LOAD_FAILED)`）；
  2. `media.paused && currentTime > 0` → 阶梯（原先是宽限 5 秒后 `stop`）；
  3. `media.paused && currentTime === 0` → **首次起播请求仍然立刻发**（走 `START` + `startRequestedKey`，不变），之后不再按 6 秒判 `playbackRefused`，而是走阶梯；
  4. `stalled` 与 `waitForPlayable` 两支**完全不动**。
- **成功判据**：**连续在播满一个间隔（5 秒）**才算成功 → 清空 `resume`。不能用「`paused === false`」：平台的 `singleton` 守卫会在 1 秒内把非令牌持有者按停，「起了又被按停」会被瞬时判据当成成功，5 次上限就悄悄变成无限。
- **清空的两种情况**：确认恢复成功；媒体换了（`key` 变了 = 另一个媒体、另开一轮）。
- **媒体中途消失（`media === null`）不清空**：账本留给同一轮故障，免得「消失 → 重现」被当成新的一轮而绕开上限。
- **重启的记忆重置口径 = 与「继续」按钮完全一致**：重置全部时间基准，**保留 `lastAction` 与 `advanceSignature`**（否则重启会导致重复点「下一节」），外加保留「已经重启过一次」这个事实（`stage = 2`），否则重启后又获得 5 次。
- **用尽后沿用原停止原因**，不新增 `STOP_REASON`。

### 第 3 步 · 等待与文案

`PENDING` 从 7 个变成 **9 个**（退 2 进 4）：

| kind | 等待什么 | 到期 |
|---|---|---|
| `AUTO_RESUME` | 第一段还有名额 | 动手：第 k/5 次续播 |
| `RESUME_RESTART` | 第一段用尽，等第 5 次的结果 | 动手：重启脚本 |
| `AUTO_RESUME_AFTER_RESTART` | 第二段还有名额 | 动手：第 k/3 次续播 |
| `RESUME_FINAL` | 第二段用尽，等第 3 次的结果 | 停下：原原因 |

| kind | 文案 |
|---|---|
| `AUTO_RESUME` | `N 秒后自动续播（第 k/5 次）` |
| `RESUME_RESTART` | `再等 N 秒仍没恢复就重启脚本` |
| `AUTO_RESUME_AFTER_RESTART` | `脚本已重启　N 秒后自动续播（第 k/3 次）` |
| `RESUME_FINAL` | `再等 N 秒仍没恢复就停下` |

- **退休** `PENDING.PAUSED`（`再等 N 秒仍暂停　将停下`）与 `PENDING.START_GIVEUP`（`再等 N 秒仍未开始播放　将判定被拒绝`），连同它们的状态条文案一起删。
- `pending` 多带两个字段（第几次 / 共几次）供文案拼；`progressText(memory)` 仍是适配层唯一的记忆入参，不新增接口。
- **不进入真正的停止态**：状态条不闪一条红的「已停下」再变回绿，重启的痕迹只体现在第二段的文案前缀「脚本已重启」上。
- 停下文案的后缀：`<原因文案> —— 已自动续播 5 次、重启后 3 次均未成功`（四档一致）。

### 第 4 步 · 用例

- 用例 57 → **约 68**。新增/改写清单：
  1. 暂停 → 满 5 秒 → 发 `autoResume`（第 1 次），`resume.attempts === 1`；
  2. 续播后**连续在播满 5 秒** → 账本清空；
  3. 起了不到 5 秒又被按停 → **只消耗名额、不清零**；
  4. 换媒体（`key` 变）→ 账本重开；
  5. 媒体消失（`media === null`）→ 账本保留；
  6. 第一段 5 次用尽 → `pending = RESUME_RESTART`；
  7. 第一段用尽满 5 秒 → **重启**：动作 `autoResume` + 记忆被重置、`stage === 2`、`lastAction` / `advanceSignature` 被保留；
  8. 第二段 3 次用尽 → `pending = RESUME_FINAL`；
  9. 第二段用尽满 5 秒 → `stop`（原因沿用）；
  10. `mediaLoadFailed` 走阶梯（不再是立刻停）；
  11. 起播支合流（原「`START_GIVEUP` 6 秒判被拒」改写成阶梯形状）。
- 改写既有两条：`PENDING.PAUSED`、`PENDING.START_GIVEUP` 的等待用例。
- 末尾两个自检必须都过（每条停止原因、每条等待）；停止原因**不增不减**，所以自检的停止原因那一半不用动。

### 实现时如实记的偏差

1. **停止原因在「停下那一刻」才算，不是阶梯起点就定下**：`media.currentTime === 0` 的一律记 `playbackRefused`，真正播过的才按**当时**的 `focus.lost` 分 `focusLostPause` / `manualPause`。于是「失焦后进入阶梯、期间回到窗口、仍没恢复」最终记 `manualPause` —— 原因反映当下，文案里的动作提示（「请回到窗口后点『继续』」）也就不会自相矛盾。
2. **`pending` 的接口多动了一处**：工单第 3 步只写「多带两个字段」，实际是 `pendingOf(kind, dueAt, extra)` 多一个入参，并且 `pendingText()` 把**整条 pending** 作为第二个入参交给文案函数（要拼「第 k/N 次」）。纯数据、仍在决策核心那一侧，没破三层边界。
3. **「重启」那一刻也会发一次播放**：`initialMemory()` 会清掉 `startRequestedKey`，所以重启后如果媒体还没起播，下一 tick 会**再发一次 `START`**（首次起播请求），与重启自带的 `AUTO_RESUME` 相隔约 1 秒；对已经播起来的情形是 no-op。如实记：这是「重启 = 从头再来一次」的自然结果，不是重复请求。
4. **阶梯的「恢复确认」块排在 `failed` 判定之前**：一个 tick 里 `failed` / `ended` / `paused` 三条出口都可能命中，而「连续在播」的计时必须每 tick 都看得到。`ended` 那一支顺手清掉阶梯（这条媒体的事已经结束）。

## 验收

```bash
node src/tests/decision.test.js        # 全绿 + 两个自检都过
```

真机（`playwright-cli -s=xuexitong`，**仓库根目录**执行，**先 `close` 再 `open --headed` 重启浏览器、只留一个章节标签页**）：

1. 装新版（`http://127.0.0.1:8123/src/xuexitong-auto-next.user.js`；首开可能不弹安装页，`reload` 一次）；
2. 让视频播起来后**把光标移出窗口**（触发平台那个 `mouseout` 暂停）→ 状态条应显示 `N 秒后自动续播（第 1/5 次）`，5 秒后**播放在没有人工干预的情况下继续**；
3. 确认续播成功后状态条回到 `还剩 Ns`（没有残留倒计时）；
4. 若一次就顶住，第二段阶梯与「重启」在真机上看不到 —— 单测覆盖即可，如实记「没验到」。

判定标准：**暂停之后播放确实自己回来了**，且回到正在播之后没有多余的倒计时。

## 明确不做

- 不给「停止」加暂停媒体（`docs/adr/0008`）。
- 不把 `stalled` / `mediaNotFound` 接进阶梯（`0009` 的 Considered Options：前者对没暂停的元素调 `play()` 是空操作，后者那一刻没有媒体元素）。
- 不做无限续播、不自动反复重启（重启只一次）。
- 不引入构建工具链 / 包管理器 / 测试运行器。

## 真机验收记录（2026-09-28）

用例 **71/71 绿、两个自检都过**。装进油猴后先核对版本（`__xuexitongAutoNext.ACTION.AUTO_RESUME === "autoResume"`），再在真实页面上验到的：

| 时刻（从「媒体被暂停」起算） | 验到什么 |
|---|---|
| +0.5s | 状态条 `5 秒后自动续播（第 1/5 次）`（动手类） |
| +0.5 → +4.5s | 倒计时按秒递减 `5 → 1` |
| **+5.3s** | `paused` 变 `false`、`currentTime` 继续前进（**全程没有任何人工干预**）；状态条改成 `5 秒后自动续播（第 2/5 次）`，约 1 秒后倒计时消失（连续在播确认完成、账本清空） |
| +0 → +29s | 第一段 5 次全部走完，每次都报「第 k/5 次」 |
| +30 → +34s | `再等 N 秒仍没恢复就重启脚本`（放弃类） |
| **+35s** | `脚本已重启　5 秒后自动续播（第 1/3 次）` —— 重启确实发生，记忆被重置后循环照常跑 |
| +35 → +51s | 第二段 3 次走完 |
| +52 → +56s | `再等 N 秒仍没恢复就停下` |
| **+57s** | 真正停下：`播放被暂停了，已停下 —— 点「继续」接着跑（已自动续播 5 次、重启后 3 次均未成功）` |

- **两条触发路径都验到了**：①把光标移出窗口（**平台的真实机制**，`paused` 当场为 `true`，5 秒后自己续上）；②在页面里反复调 `video.pause()`（用来把阶梯耗到终局）。两者表现一致。
- 终局记下的原因是 `manualPause`（当时窗口仍有焦点）—— 与设计一致：光标移出窗口 ≠ 窗口失焦，两者决定记哪一条。
- **「继续」的重置口径顺带验到**：按下后状态条回到「正在运行」，下一次暂停又是完整的「第 1/5 次」（`stage` 与「已重启过」一起被重置）。
- ⚠️ **如实记一条观感**：按「继续」之后媒体**没有立刻**恢复，而是先起了一轮新的阶梯（`1 秒后自动续播（第 1/5 次）`），5 秒内自己续上 —— `adapter.playOnce()` 那次 `play()` 没当场生效（`paused` 仍为 true）。这恰好说明阶梯不是多余的：单次 `play()` 并不总是立刻管用。
- **消耗与副作用（如实记）**：验收期间反复 `pause()` 把媒体按停约两分钟（暂停只让上报停住，**没有**伪造任何观看时长）；终局那一次脚本真的停下了，随后用状态条的「继续」恢复；期间用户手工点过一次「停止」→「继续」（正好验到重置）。**没有**代为确认任何确认框。
