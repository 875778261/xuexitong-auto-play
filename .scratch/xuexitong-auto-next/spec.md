# Spec — 学习通「自动播放下一节」油猴脚本

Status: ready-for-agent

## Problem Statement

在目标站点上刷一门课，需要逐个任务点把视频（和音频）看完，每个看完后手动点一次「下一节」，一门课 317 个任务点意味着几百次"看完—点击"的机械重复。更麻烦的是站点有防挂机机制：鼠标移出窗口会让播放暂停，人一离开就停在那里，回来才发现进度没走。学习者被迫守着屏幕，守着也只是为了点那一下。

## Solution

一个油猴脚本，加载在目标站点的学习页面上，自己完成"播放 → 播完 → 推进"这个循环，一路跑到整门课结束：

- 自动找到**第一个未完成的任务点**并零点击起播（有声，不需要静音）；
- 视频自然播完后固定等 15 秒，再推进到下一个任务点，跨任务点、跨节点、跨章不停；
- PPT 任务点视为复习材料，不计入需完成范围（见 ADR 0003）；
- 页面角落有一条**状态条**，随时显示"正在做什么、为什么停下来"；
- 失焦暂停、加载失败、播放卡住这三类情况**停下并提示**，绝不静默重启播放；
- 用户随时可按**一键恢复**继续，或停掉脚本。

脚本只做一件事：**如实播完，然后推进**。不改 `currentTime`、不伪造上报字段、不跳过未完成的媒体任务点（见 ADR 0002）。

## User Stories

1. 作为学习者，我想让脚本自动找到当前章节里第一个未完成的任务点，这样我不用自己在章节树里翻找进度。
2. 作为学习者，我想让视频零点击自动起播且有声音，这样我不用先点一下播放按钮、也不用被迫静音看课。
3. 作为学习者，我想让脚本在一个视频播完后自动推进到下一个任务点，这样我不用守着点「下一节」。
4. 作为学习者，我想让这个"播完 → 等待 → 推进"的循环一路跑完当前节点的所有任务点，这样我不用中途接手。
5. 作为学习者，我想让脚本在节点内任务点全部完成后自动跨越到下一节点，这样整章不用我逐个点。
6. 作为学习者，我想让脚本跨章继续推进，这样一门课可以一次跑完。
7. 作为学习者，我想让脚本在整门课都完成后停下来并明确告诉我"已完成"，这样我知道什么时候真正结束了。
8. 作为学习者，我想让脚本在播放期间于页面角落显示一条状态条，这样我瞄一眼就知道它现在在做什么。
9. 作为学习者，我想在状态条上看到当前任务点在整门课里的**数量进度**，这样我能判断还剩多久。
10. 作为学习者，我想让状态条显示当前任务点的已播时长/总时长，这样我能看出它是不是卡住了。
11. 作为学习者，我想让脚本在视频因**窗口失焦**而暂停时停下来并显式提示，这样我知道暂停不是脚本坏了（见 ADR 0002）。
12. 作为学习者，我想在这个提示上有一个**一键恢复**按钮，这样我不用去研究该点页面哪里。
13. 作为学习者，我想让脚本**不静默续播**失焦后的视频，这样上报的观看时长始终对应真实的观看（见 ADR 0002）。
14. 作为学习者，我想让脚本在视频**加载失败**时停下并提示，而不是无限重试或跳过。
15. 作为学习者，我想让脚本在**播放卡住**（`currentTime` 长时间不前进）时停下并提示，这样我不用盯着进度条猜。
16. 作为学习者，我想让脚本遇到 **PPT 任务点**时不尝试播放、把它当作复习材料跳过去（见 ADR 0003）。
17. 作为学习者，我想让脚本在**只剩 PPT 未完成**时自动点掉确认框里的「下一节」继续推进，这样纯 PPT 节点不会打断整门课的自动化（见 ADR 0003）。
18. 作为学习者，我想让脚本在**媒体任务点未完成的确认框**出现时停下并提示、不代为确认，这样脚本不会替我跳过还没看的视频（见 ADR 0002）。
19. 作为学习者，我想让脚本处理**音频任务点**，这样音频类型的任务点不必我另外手动听一遍。
20. 作为学习者，我想让脚本在遇到**启用人脸抓拍**的课程时直接放弃并说明原因，这样我不会白白等它（见 ADR 0002）。
21. 作为学习者，我想让脚本在检测到**多端登录风控**（弹窗警告 / 被踢回登录页）时停下并提示，这样我知道是账号在用别处而不是脚本失效。
22. 作为学习者，我想让脚本每次页面就绪都**从"找第一个未完成任务点"重新开始**，这样无论「下一节」是整页重载还是局部刷新，它都能续上（见 ADR 0002 之外的幂等设计）。
23. 作为学习者，我想让脚本**不依赖任何跨页保存的状态**，这样我手动刷新页面、手动跳章节之后它依然能正确接上。
24. 作为学习者，我想让脚本能正确处理**学习页面里的多层 iframe**，这样任务点内容虽然藏在里面也不会被漏掉。
25. 作为学习者，我想让脚本**只在目标站点的学习页面上生效**，这样我正常浏览其它页面时它完全不打扰。
26. 作为学习者，我想有一个**停止**入口，这样我随时能中断自动推进、自己接手。
27. 作为学习者，我想让脚本在我自己手动操作（手动暂停、手动点下一节、手动跳章）时不与我抢控制权。
28. 作为学习者，我想让脚本在推进后**先确认下一个任务点真的就绪**再起播，这样不会在页面还没加载完时白等。
29. 作为学习者，我想让脚本**绝不修改 `currentTime`**、绝不伪造 `isdrag` 之类的上报字段，这样观看记录始终是真实的（见 ADR 0002）。
30. 作为学习者，我想让脚本在启动时**不弹出任何需要我确认的对话框**，这样它是装上就干活、不需要每次应答。
31. 作为学习者，我想让脚本的行为在**同一门课上可重复**——今天跑一半关掉、明天再跑，结果一致。
32. 作为脚本维护者，我想能在一个**调试句柄**上直接喂状态、断言脚本决定的下一个动作，这样我在不跑整门课的前提下就能验证推进逻辑。
33. 作为脚本维护者，我想让"什么情况下停下"是**可枚举、可断言**的，这样新增一类异常时不会破坏已有的停止条件。

## Implementation Decisions

**交付形态**：单个油猴脚本文件，头部带元数据块，由浏览器扩展直接加载。仓库**不引入**构建工具链与包管理（承 ADR 0001 的结论）；本 spec 的实现不引入打包器。

**循环单位**：层级是三级——**节点 → 卡片 → 任务点**。一个节点下有若干**卡片**（`ul.prev_ul > li#dctN`，带 `title` 标签与 `cardid`），**同一时刻只有 `active` 那张卡片的内容被渲染出来**，其余在 DOM 里根本不存在；而一张卡片会把它全部任务点一次渲染出来。循环与进度的单位仍然是**任务点**（它才是完成判定的单位）；卡片是「同一节点内任务点的分组与切换方式」。

**找「下一个未完成任务点」的顺序写死为**：从第 1 张卡片起，找第一张**含未完成任务点**的卡片；在该卡片内按 DOM 顺序找第一个未完成的任务点。这样无论「下一节」是整页重载还是局部刷新、也无论用户是否手动刷新过页面，结果都一致。

**任务点的类型一律按它内部模块 iframe 的 `src` 判定**（`/ananas/modules/video/` 视频 | `/ananas/modules/audio/` 音频 | `/ananas/modules/pdf/` PPT），**不看卡片标签**——标签只是标签，任何一张卡片里都可能混着视频与音频。认不出的类型停下提示，不猜。（⚠️ 已被 `docs/adr/0006` 与 `0007` **改写**：任务点先按 **`jobid`** 认，读不到 `jobid` 的容器是**资料附件**、根本不算任务点；读得到 `jobid` 但模块类型不认识的，归入「**脚本播不了的任务点**」一档，**跳过而不是停下**。）

**模块划分（三个职责，同一文件内）**：

1. **决策逻辑**——纯函数：输入是一份**观察值**（当前节点内的任务点列表及其完成标记、活跃媒体的可读状态、当前时刻、上次观察的时刻），输出是一个**动作**（起播 / 等待 / 推进到下一个任务点 / 替用户确认推进 / 停下并给出原因）。它不读 DOM、不碰计时器、不产生副作用。
2. **站点适配层**——唯一知道目标站点 DOM 的地方：遍历多层 iframe 找出节点内的任务点、读取每个任务点的完成标记与类型、取得当前活跃的媒体元素、点击「下一节」、识别并点击确认框、渲染状态条。它是决策逻辑的观察值与动作的**执行端**。
3. **驱动循环**——按固定间隔采样（由适配层取观察值）→ 交给决策函数 → 执行它返回的动作。这是**唯一**的副作用来源。

**动作集（就是上面那条缝的接口）**：起播、等待、推进任务点、确认推进、停下（带原因）。停止原因需可枚举，至少覆盖：媒体未完成需人工确认、失焦暂停、加载失败、播放卡住、人脸抓拍课程、多端登录风控、整门课已完成、用户手动停止。

**播放时序**：

- `play()` **零点击直接调用**（该域 autoplay 授权已实测生效，无需静音降级）；保留一个最简兜底——`play()` 被拒时归入"停下并提示"，不重试、不静音重试。
- 时长在起播前不可读（`preload="none"`），所以**总时长在 `play()` 之后才采集**。
- `ended` 之后**固定等待 15 秒**再推进。这个常量是实现参数，需集中在一处便于调整。
- 播放期间以固定间隔采样 `currentTime`，"长时间不前进"判据基于两次采样的差值，而非绝对时长。

**推进方式**（⚠️ 已被 `docs/adr/0010` **改写**）：本节点内还有可播（视频 / 音频）的未完成任务点时**就地播**，不跳——先在本卡片内播完，再切到下一张卡片继续。本节点确实没有可播单元之后，**从章节树直接跳到当前节点之后第一个未完成节点**（只向前；判据是树上 `input.jobUnfinishCount` 存在，见 ADR 0010）。原来那条「点『下一节』→ 平台弹确认框 → 代为点确认框里的『下一节』（`a.bluebtn02.prebutton.nextChapter`，ADR 0005）」**降级为章节树不可用时的回退路径**。

判定「只剩 PPT」**必须遍历本节点的全部卡片**：章节树给的 `input.jobUnfinishCount` 把 PPT 也算进去，不能当判据。除此之外的确认框（即还有未完成的**媒体**任务点）一律停下提示（ADR 0002）。「下一节」的跳转是整页重载还是局部刷新**未知**，两种情形都由幂等覆盖。

**幂等**：不保存任何跨页状态，不依赖 `localStorage`。每次页面就绪都重新采样、重新选"第一个未完成的任务点"。这是刻意设计，用来免疫跳转方式未知与用户手动刷新。

**状态条**：渲染在页面角落，与页面样式隔离，不遮挡站点自身的操作控件。内容为"当前动作 + 进度（已完成/总任务点）"。停下时在状态条上显示原因与一键恢复入口。

**停止边界（承 ADR 0002 与 ADR 0005）**：不修改媒体时间轴、不伪造任何上报字段、不跳过未完成的媒体任务点、不静默续播失焦暂停、不在媒体确认框上代用户按确认。

**已知未知（不阻塞实现，实现时页面就在眼前，当场确认）**：

- 「任务点已完成」在 DOM 上的标记未亲眼确认（目前只见过未完成侧）——判错只会白播一遍，进度不会倒退。
- 「下一节」是整页重载还是局部刷新——**不必探明**。
- 音频任务点的 DOM 结构与上报路径未探查（视频的那套已确认：播放期间按已看时长增量上报，`isdrag` 是"是否拖动过进度条"的判定位）。
- 「只剩 PPT 未完成」时点「下一节」是否真的弹确认框——默认按"会弹框、需代为确认"实现。

## Testing Decisions

**什么是好测试**：只喂**观察值**、断言**动作**。不触碰 DOM、不等待真实时间（"当前时刻"是入参）、不依赖任何目标站点的选择器。一条测试 = 一段状态 → 一个动作。

**测试缝只有一处**：上面那条**纯决策函数**。这是仓库里唯一的可测边界，也是最高的一条——DOM 细节、计时、点击全部被推到它外面。选择它而不是别的缝，是因为它能覆盖脚本里"什么时候推进、什么时候停下"的全部判断，而那正是唯一会出错、也唯一危险的部分（推错了会跳过没看的视频）。

**在什么上面跑**：脚本在目标站点页面上暴露一个**调试句柄**（挂在页面全局），把决策函数与一条"用给定观察值求动作"的入口暴露出来。用例写在**探查会话**里，用浏览器 CLI 的求值命令驱动句柄、打印断言结果——**这就是红-绿回路**。用例本身落在仓库中（不进 `.scratch` 之外的产物目录），随脚本一起演进。

**剩下的缝不硬凑**：iframe 遍历、`play()` 授权、`ended` 时序、状态条渲染这些无法脱离真实页面验证的部分，用**少量端到端**跑真实页面确认，靠状态条与页面控制台观察。不为它们造假测试、不为此引入测试运行器或打包器。

**Prior art**：仓库内**没有**先例——这是第一个油猴脚本，没有 `package.json`、没有测试运行器、没有可参照的既有测试。本 spec 建立的"纯决策函数 + 页面调试句柄 + 探查会话跑用例"就是本仓库的第一份 prior art，后续脚本应复用它。

**回归的形态**：因为"停下"的条件是可枚举的，回归测试的主体就是**每条停止原因一条用例** + 正常推进路径的若干条用例。新增异常类型时，先补一条停止原因的用例。

## Out of Scope

- **PPT 的自动播放与自动翻页**：PPT 仅作复习，不计入需完成范围（ADR 0003）。
- **人脸抓拍课程**：这类课程无法自动化，脚本直接放弃（ADR 0002）。
- **多端登录风控的规避**：脚本只做提示，不尝试绕过；使用纪律是单端登录。
- **构建工具链 / 包管理 / 单元测试运行器**：本 spec 不引入打包器（见 Implementation Decisions）。
- **倍速播放、跳转、静音后台播放**等"让观看更快"的手段：与 ADR 0002 直接冲突。
- **任务点的完成判定由脚本自行改写**：完成与否一律以站点给出的信息为准，脚本只读不写。
- **其它目标站点**：一个脚本只服务一个目标站点。

## Further Notes

- **实测数据**：同一节点下三个视频长度分别为 88 / 235 / 256 秒；整门课 317 个任务点。任何"跑完全程要多久"的估算都基于这些数字，且它们会随课程变化。
- **探查期间的副作用，如实记录**：为验证自动播放与上报接口，探查期间真实播放过一个视频约 20 秒，产生两次进度上报（`playingTime=0`、`playingTime=20`），远低于 90% 判定线，**未**把该任务点标成完成。另触发过一次多端登录风控（探查用 Chrome 与日常 Edge 同时登录），表现为弹窗警告 + 探查会话被重定向到登录页。
- **敏感信息**：站点事实文档与探查产物中含有平台内标识（courseId / clazzId / personid / userid / objectId 等），不要外传；浏览器 profile 含真实登录 cookie，**绝不**提交或分享。
- **相关决定**：ADR 0002（只做如实完播后的推进）、ADR 0003（PPT 不计入需完成范围）、ADR 0001（探查用 CLI 而非 MCP）。
- **下一步**：按本仓库约定，实现 ticket 落在 `.scratch/xuexitong-auto-next/issues/` 下；本 spec 已标 `ready-for-agent`，可直接交给 `/implement`。

## Comments

实现落在 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`（37 条用例，`node src/tests/decision.test.js`）。与 spec 的偏差，如实记：

1. **测试缝的驱动方式改了**。spec 的 Testing Decisions 写「用例用浏览器 CLI 的求值命令驱动调试句柄」；实际改成**零依赖的 node 运行器**——用例把脚本文件丢进 `node:vm` 加载、取句柄、喂观察值断言动作。同样是一个命令的红-绿回路，但不需要浏览器、不碰探查会话、不受登录态与风控影响。脚本仍然暴露调试句柄（收敛到 `decide` / `initialMemory` / `ACTION` / `STOP_REASON` / `CONSTANTS`）。
2. **US9「整门课的数量进度」只做到「本节进度」**。整门课的任务点总数要读章节树，未探查，所以状态条只报当前节点的进度（文案也从「节点进度」改成「本节进度」，避免名不副实）。
3. **US27 只做了一半**。「手动暂停」会停下（有专门用例）；「手动点下一节 / 手动跳章」没有专门检测——靠幂等重新接手，不试图回退到旧状态。
4. **`play()` 被拒的兜底更紧了**。spec 说「不重试」，实现为：同一个媒体只请求一次起播，请求后仍停在起播前超过 6 秒即判定被拒并停下。
5. **加了几样 spec 没写的东西**，都是为了让改动安全：同类动作的冷却（含「页面没变化时 8 秒内不重复点下一节」）、页面查询的短缓存、以及在「读到已无未完成任务点却仍弹确认框」时新增的停止原因 `dialogWithoutUnfinished`。

### 2026-09-28：当场确认后，模型被推翻，spec 待重写

上面那句「四条未确认事实集中在 `ADAPTER_FACTS`、改一处即可」**不成立**。确认的结果动到了模型本身：

1. **层级少了一层。** 真实结构是「节点 → **卡片**（`ul.prev_ul > li#dctN`，按内容分组，一次只渲染一张）→ 任务点」，spec 只有「节点 → 任务点」。`input.jobUnfinishCount` 是**整节点跨全部卡片**的未完成数（实测 2 视频 + 11 音频 = 13，与节点计数吻合），而 DOM 里永远只有当前卡片那一批——这才是脚本「本卡片播完就去点下一节、于是撞上确认框」的根因。术语见 `CONTEXT.md`。
2. **PPT 的结论被推翻。** `0003` 的「PPT 不计入需完成范围」作废，改为「PPT 同样要完成，方式是把内容拉到最底端」（滚到底触发一次 `job/document`，返回「添加考核点成功」）——见 `docs/adr/0004`，`0003` 已标 superseded。连带 `CONFIRM_ADVANCE` 退化为「脚本判断出错」的兜底探测。
3. **任务点类型不能按文案判定。** 类型只写在模块 iframe 的 `src` 上（`/ananas/modules/video/` | `/ananas/modules/audio/` | `/ananas/modules/pdf/`）；`ans-job-icon` 的类名对音频与 PPT 是空的。spec 里「视频 / PPT / 音频三类」的说法也不成立——卡片标签实测出现过第四种。认不出的类型应停下提示。
4. **人脸上报参数的位置**只出现在当前卡片的文档里（`iframe#iframe` 的 `<script>`），只扫主文档会漏检。
5. **`ADAPTER_FACTS` 之外还有两处实现缺陷**（不属于模型问题）：`findMedia()` 会选中每个卡片文档里那个 `src=""` 的隐藏 `<audio id="auditionAudio">`；`searchableAttrs()` 不读 `aria-label`，而「任务点未完成」恰恰只写在那儿。

**由此 spec 的两节需要重写**（本轮只落文档，代码与测试另起一轮）：

- `Implementation Decisions` 的「**循环单位**」——改为三级，并写死顺序：**从第 1 张卡片起，找第一张含未完成任务点的卡片，再在该卡片内找第一个未完成的任务点。**
- `Implementation Decisions` 的「**推进方式**」——加入卡片遍历与新的 `completePpt` 动作（PPT 拉到最底端，判据是容器出现 `ans-job-finished`）。

`Testing Decisions` 不变，仍是一条停止原因一条用例。

### 2026-09-28 第二轮：PPT 再改向，规则请回 `0003`，理由换成「跨域」

上一节把 PPT 的结论改成「同样要完成，方式是把内容拉到最底端」（`0004`）。当场验证时发现**脚本做不到**：PPT 的内容框架 `iframe#panView` 会 302 跳到 `pan-yz.chaoxing.com`——**另一个域**，父页面读不到它的 DOM、也驱动不了它的滚动（平台恰恰把滚动处理挂在它的 `onload="bindScroll()"` 上）。

于是定案（`0005`，取代 `0003` 与 `0004`）：**PPT 不由脚本完成；本节点内只剩 PPT 未完成时，脚本点「下一节」并代为确认确认框。** 规则与 `0003` 相同，理由换成「脚本在技术上够不到它」，并如实接受代价：PPT 没做完，节点在平台上就一直显示未完成。

**⚠️ 因此本文里所有 `ADR 0003` 的引用（Solution 的 PPT 那条、US16、US17、Further Notes）都应读作 `ADR 0005`。** 规则未变，只有理由与编号变了；没有逐处改写是为了不把 US 编号与已有交叉引用打散。

**本轮就地改写的两节**：「**循环单位**」（三级层级、写死查找顺序、类型只看模块 `src`）与「**推进方式**」（本节点还有可播任务点时不点「下一节」；只在只剩**脚本播不了的任务点**时才点并确认——范围见 `0007`）。其余各节与 `Testing Decisions` 不变。

**仍然未知、但不阻塞实现的只有一条**：「下一节」的跳转是整页重载还是局部刷新——幂等设计覆盖两种情形。

### 2026-09-28 第三轮：按 ticket 01 落地（卡片层 + 跳过 PPT），与工单的偏差如实记

实现落在 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`（48 条用例）。

1. **工单第 1 步第 2 条与实际代码不符**：`searchableAttrs()` 那版**已经在读 `aria-label`**，不是漏读。改用容器模型后它连同 `classify()`（按文案/类名猜类型）一起**整个删掉**——任务点只按 `.ans-attach-ct` 容器识别、只按容器类判完成、只按模块 `src` 判类型，不再按文案或 `aria-label` 找任何东西。

5. **Tampermonkey 没装成**：用本地 http 服务 + `.user.js` URL 唤起了油猴安装页并点了「安装」，但油猴的脚本列表仍是空的（没落库），所以适配层端到端改用 `page.addInitScript` 把脚本本体注入真实页面来做——同样跑真实页面、真实 DOM，只是少了扩展这一层。检查清单里的四条都过了。
6. **两轴评审后又改了四处**（Standards + Spec 各提了一条实质问题）：
   - 状态条文案 `本节 x/y` 改成 `本卡片 x/y`。`CONTEXT.md` 的术语表把「节」列为该回避的词；工单验收里那句「状态条报出本节 x/y」的本意就是「当前卡片」的进度。
   - **切卡片的顺序按 spec 写死**：动作 `openTaskPoint` 现在带一个 `card` 字段，值是「还没找过的卡片里序号最小的那张」（= 从第 1 张卡片起），由适配层照它切；不再用「当前 +1 环状」。
   - **卡片层认不出来时**（有切换器却没有活动卡片）不再退回「只有一张卡片」——那会在纯 PPT 卡片上把「只剩 PPT」判成立而代为确认，可能跳过别的卡片里没看完的视频。现在按「没找遍、也没法切」处理：不切卡片、原地等超时停下，提示文案点明这个可能。
   - `docs/sites` 里那几个「某张卡片有几个任务点」的实例数字删掉了（该文件自己写着「任务点数量不写进来」，会过期）。

### 2026-09-28 第四轮：任务点改按 `jobid` 认；只剩资料附件的节点直接推进（`docs/adr/0006`）

起因：用户在学习页上撞到停止原因 `unknownTaskPointKind`（「有个未完成任务点的模块类型认不出来…不猜着处理」），并指出那几个节点其实只是**资料展示**。

探查（真实页面；两道保险：`HTMLMediaElement.play` 打死、带 `PCount.next` 的点击拦住，全程没有播放、没有代为确认）得到的四条事实，已写进 `docs/sites/xuexitong.md`：

2. 平台不把这些当任务点：章节树上这几个节点没有 `jobUnfinishCount` 数字（而「2.3 四级解题技巧视频精讲」有「8」）；从它们推进**不弹**「还有任务点未完成」（`PCount.next` 里 `checkJob()` 为假）。**所以跳过它们不需要任何「代为确认」的授权，`0002` 的边界没有动。**
3. 对照真任务点（`2.3` 的 8 个视频）：容器有 `ans-job-icon`、iframe 有 `jobid`。**判据是 `jobid`，既不是容器、也不是模块类型。**
4. 「下一节」是**局部刷新**，不是整页重载（状态条上停住的旧判定连续跨三次换节都没被重置；`performance.now()` 显示文档已开了 96 秒）。推论：脚本实例跨节点存活，**停一次不是断一次，是从这里往后都不再推进**——`docs/sites` 里挂着的那条「尚未确认」到此结案。

实现落在 `src/xuexitong-auto-next.user.js` 与 `src/tests/decision.test.js`（53 条用例，`node src/tests/decision.test.js`）：

- **适配层**：`scanTaskPoints()` 只收**带 `jobid`** 的容器（新增 `jobIdOf()`，属性与 `data.jobid` 两处都读；原来的 `taskPointId()` 兜底 id 删掉——那正是把资料附件算成任务点的原因）。

- 停止原因 **`taskPointsNotFound` 删除**（连同它的用例）——它守的位置被上面那条接管，留着就永不触发；用例文件末尾的自检会逼你做这个决定。`input.jobUnfinishCount` 从此**只用来显示进度，不参与决策**。（⚠️ **这一句已被 `docs/adr/0010` 推翻**：它现在正是「选下一个要跳过去的节点」的判据。）

**与用户原话的两处差异，如实记**：

- 用户的第 1 条要「认不出类型 + 没有其他卡片 → 直接下一节」。实现**没有**这样改，因为判据找错了位置：资料附件不是「未知类型的任务点」，它**根本不是任务点**。改完之后 `unknownTaskPointKind` 只对**带 `jobid` 的真任务点**生效，仍然停下（理由见 `docs/adr/0006` 的 Considered Options：那种情况平台会弹确认框，「推进」就绕回 `0002` 的授权问题）。
- 用户的第 2 条「其他未知的情况也直接下一节」落在「本卡片 0 任务点 → 推进」这条规则上。用户明确否掉了「用 `jobUnfinishCount` 做交叉校验」：**平台说有未完成而脚本采不到时，也照样推进，不停**。（⚠️ **这一条也已被 `docs/adr/0010` 反转**：树跳转绕开了平台的确认框，安全网改由章节树上的计数承担——「树上说有未完成、脚本却一个未完成任务点都没采到」现在会**停下**。）

**同日补记（`docs/adr/0007`）：认不出类型的任务点也跳过。** 上面「与用户原话的第 1 条差异」被推翻了 —— 用户在真机上验收后明确要求：**带 `jobid` 的真任务点、模块类型不认识时，跳过即可，不用停。** 于是：

- 停止原因 `unknownTaskPointKind` **删除**（连文案与用例）。
- 「脚本播不了的任务点」定义成 `!isPlayableUnfinished(t)`：PPT ＋ 认不出类型的一切未完成任务点，一律**扫遍本节点全部卡片后跳过**，平台弹「还有任务点未完成」时**代为确认** —— `0002` 的例外因此从「只剩 PPT」扩成「只剩脚本播不了的任务点」（取舍与代价见 `docs/adr/0007`）。

**真机验收（同一天，装进油猴后实测；用例 57/57 绿）**——验到的：

**没验到的四条，如实记**：

1. **`ADVANCE_DELAY`（播完等 15 秒）在真机上看不到**，是一条**行为发现**：`findMedia()` 的打分给「已播完」的元素 +2，所以一条媒体播完后，只要本卡片还有别的未完成任务点，脚本当场就会选中**下一个**媒体（`paused` + `currentTime === 0` → 直接 `START`），`media.ended` 那一支根本轮不到——「播完固定等 15 秒」实际上只在**本卡片最后一个可播任务点**播完时才走到。要观察到它就得等一个节点播到最后一个媒体，而本课程里「只剩 1 个未完成」的节点（`2.4`）是个 1753 秒的视频。**这条行为差异不是本轮引入的**（`findMedia` 的打分没动过），是否要改留作下一轮。
2. **`START_GIVEUP`（起播被拒）**：需要浏览器拒绝自动播放，本机域级 autoplay 授权是放行的，造不出来。
3. **`STALLED`（进度停顿）**：需要真的卡一次，没等到。
4. **两种 `confirmAdvance`（只剩 PPT / 只剩认不出类型的任务点）与 PPT 的 `jobid` 复验**：本课程**没有找到真 PPT 任务点**（`pdf` 模块）——第二轮与第四轮各找过一次，这次又看了 `2.4`（单个 1753 秒视频）、`3.1`（三张卡片，全是音频），仍然没有。要确认这门课到底有没有，得把 18 个 Unit 节点只读扫一遍（约十几分钟、会真的播放），**留给用户点头**。

### 2026-09-28 第六轮：暂停后自动续播 —— 两段阶梯（`docs/adr/0009`、`issues/03-auto-resume-ladder.md`）

走的是 `/grill-with-docs`：三轮编号提问、每题带推荐答案，用户逐条「使用推荐」。这一轮**反转了本 spec 自己的一条边界**，起点是用户的一个请求（「视频自动暂停后、或脚本自动停止后，尝试 5 次自动继续，间隔 5 秒」）加一条补记（「5 次失败后停止脚本、再开始一次脚本、尝试三次」）。

先说**读代码 + 只读探查拿到的三条事实**（全程没有播放、没有重启会话、没有动 DOM）：

1. **`ADR 0002` 的第二条被否选项就是它。** `0002` 的 Considered Options 明确写过「失焦暂停后静默自动续播」被放弃，理由是「等于人不在时也产生观看时长」。所以这一轮的第一件事是让用户显式认下这个反转（落 `0009`），不是直接写代码。
2. **防挂机的实现被读出来了**（已写进 `docs/sites/xuexitong.md`）：不在同源内联脚本里（当前学习页 10 个同源文档、25 个含内联代码的 `<script>` 里 `visibilitychange` / `document.hidden` / `mouseleave|mouseout` / `.pause()` 的命中数**全是 0**），而在外链 bundle `videojs-ext.min.js` 的 `studyControl` 插件里：监听绑在**播放器元素**上的 `mouseout`，且 `relatedTarget` 为空（光标真的离开窗口）才暂停 —— **一次性事件、不轮询、回窗口平台不自动恢复**。这同时**精确化了上一轮记的「判据在更底层、派发 `mouseleave`/`blur` 触发不了」**：监听挂在元素上，文档级合成事件打不中它。推论：**脚本 `play()` 一次就能顶住**，这正是阶梯有把握成立的前提。
3. **开关关不掉**：插件选项 `enableSwitchWindow`（= 1 时不暂停）在**构造时读进闭包**，事后改不动 —— 「干脆把它关掉」这条路走不通，只剩「暂停后重新 `play()`」。另外 `singleton` 那个 1 秒轮询的「同一时刻只有一个播放器能播」守卫，是「`play()` 调用成功 ≠ 真的在播」的现成理由。

用户确认的决定：

1. **反转边界**：接受「人不在屏幕前时脚本也让播放继续、平台照常上报观看时长」，代价如实写进 `0009`。用户补记的定性：这个暂停是**前端开发人员失误**加进来的、项目本身不要求，本脚本是**临时处理方案**；`docs/sites` 里平台自陈的完成条件文案**作为原始证据保留**，不再当行为依据。
2. **适用范围四档**：`focusLostPause`、`manualPause`、`playbackRefused`、`mediaLoadFailed`；**用户按「停止」永不自动续播**（`0008` 不动）。`manualPause` **必须**在名单里：平台按一次性 `mouseout` 暂停、脚本按 `document.hasFocus()` 分类，**光标移出窗口但窗口仍有焦点**时会被算成 `manualPause` —— 只留 `focusLostPause` 会做成一个永不触发的功能。代价如实记：**用户自己在播放器上点的暂停也会被自动续播**，逃生口只有状态条的「停止」。
3. **两处反转一起记**：①`0002` 的「不静默续播」；②本 spec 的 Implementation Decisions「`play()` 被拒时归入停下并提示，**不重试**」—— 现在首次起播请求之外最多再重试 8 次。
4. **两段阶梯**：5 次 → **重启一次脚本** → 3 次，间隔都是 5 秒；总窗口 50 秒；重启**只一次**，用尽后真正停下。停下的文案沿用原停止原因 + 后缀「已自动续播 5 次、重启后 3 次均未成功」。
5. **成功判据是「连续在播满一个间隔（5 秒）」**，不是「`paused === false`」—— 否则平台的 `singleton` 守卫（1 秒内按停非令牌持有者）会把「起了又被按停」判成成功，5 次上限悄悄变成无限。
6. **`stalled` 与 `mediaNotFound` 摘出去**（`0009` 的 Considered Options）：前者媒体 `paused === false`，对没暂停的元素调 `play()` 是空操作；后者那一刻根本没有媒体元素，而且它本来就在每 4 秒重试定位。接进来只是各多花 25 秒空转。
7. **不新增停止原因**：沿用原原因 + 后缀，保住「为什么停」这个信息。
8. **`PENDING` 用 4 个新 kind**（`AUTO_RESUME` / `RESUME_RESTART` / `AUTO_RESUME_AFTER_RESTART` / `RESUME_FINAL`），而不是 2 个 kind + 变体参数 —— 理由与上一轮同：自检只认 kind，漏掉一条变体的症状正是用户抱怨过的那个。同时退休 `PENDING.PAUSED` 与 `PENDING.START_GIVEUP`。
9. **不进入真正的停止态**：状态条不闪一条红的「已停下」再变回绿，重启的痕迹只体现在第二段文案的前缀「脚本已重启」。
10. **`CONTEXT.md` 不动**（沿用第五轮的先例：站点词表只放领域名词，「停止 / 继续 / 续播」的语义归 ADR）；`docs/commit-message/` 加进 `.gitignore`（该目录当前并不存在、也从未被跟踪，属预防性忽略）；提交仍拆两次：文档先行、`feat` 随后。

**真机验收（同一天，装进油猴后实测；用例 71/71 绿、两个自检都过）**：两段阶梯全跑通 ——

- **真实机制那条**：把光标移出窗口（平台的 `mouseout`），状态条当场报 `5 秒后自动续播（第 1/5 次）`，倒计时 5→1，**第 5.3 秒媒体自己续上**（`paused` 变 false、时间继续走，全程无人工干预），再 1 秒后倒计时消失（连续在播确认、账本清空）。
- **耗到终局那条**（反复 `video.pause()` 使它无法取得连续在播）：`第 1/5 次 … 第 5/5 次` → `再等 N 秒仍没恢复就重启脚本` → **`脚本已重启　5 秒后自动续播（第 1/3 次）`** → 3 次走完 → `再等 N 秒仍没恢复就停下` → **约 57 秒后真正停下**：`播放被暂停了，已停下 —— 点「继续」接着跑（已自动续播 5 次、重启后 3 次均未成功）`。终局记的是 `manualPause`（当时窗口仍有焦点），与「光标移出窗口 ≠ 窗口失焦」的设计一致。
- 「继续」的重置口径顺带验到：按下后下一次暂停又是完整的「第 1/5 次」。
- ⚠️ **如实记一条观感**：按「继续」后 `playOnce()` 那次 `play()` **没有当场生效**（`paused` 仍为 true），是阶梯在 5 秒内把它捞回来的 —— 这恰好说明单次 `play()` 并不总是够，阶梯不是多余的。
- 消耗与副作用（反复按停约两分钟、终局停下后用「继续」恢复、期间用户手工点过一次「停止」→「继续」、没有代为确认任何确认框）全记在 `issues/03` 的真机验收记录里。

### 2026-09-29 第七轮：推进改成「从章节树直接跳到下一个未完成节点」（`docs/adr/0010`、`issues/04-tree-jump-navigation.md`）

走的是 `/grill-with-docs`：三轮编号提问、每题带推荐答案，用户逐条「使用推荐」。起因是用户的一条实测：**打开开头的节点、但前面一大段早已完成时，脚本一个节点一个节点地走完那一段**——每个节点一次局部刷新，还会在每个已完成节点里 `play()` 一次它的媒体（日志里一串 `playingTime=0` 上报）。他的要求：**只经过未完成的节点，检查未完成的节点里有没有可播的任务点**；以某课程为例，1.1–3.9 全已完成，从 1.1 打开就应该直接进 4.1。

**只读探查拿到的四条事实**（都已写进 `docs/sites/xuexitong.md` § 章节树与跳节点）：

1. **整棵章节树就在学习页的主文档里**（`#coursetree`，由 `mycourse/studentstudycourselist` 铺满；服务端那份 HTML 里是空的）。每个「节」= `div.posCatalog_select#cur<chapterId>`，当前节点带 `posCatalog_active`；已完成 = `span.icon_Completed`，未完成 = `input.jobUnfinishCount`，**两者互斥**，而**只有资料附件或空内容的节点两个都没有**。
2. **跳节点的入口就是站点自己的** `span.posCatalog_name[onclick=getTeacherAjax(courseId, clazzid, chapterId)]`。实测（同一门课 2.3 → 4.1 → 4.2）：一次 `studentstudyAjax` 换掉 `#mainid`，**不整页重载**（`window` 全局与脚本实例都活着）、**跨章不需要 `changeCapter`**、**不弹「还有任务点未完成」确认框**（`checkJob()` 只写在 `PCount.next` 里；从仍有 1 个未完成任务点的 4.1 直接跳走，两个弹层都是 `0×0`）。
3. **跳过去之后树不会自己刷新**（跳转只产生 `studentstudyAjax` + `validatejobcount`，后者只回字符串 `"true"`）。所以选目标不能假设树是新鲜的，也不能拿它当实时计数源。
4. 树上 39 个节节点**全部**带 `getTeacherAjax` 的 onclick，没有锁定态。

用户确认的决定（全部按推荐）：

1. **导航机制**：树跳转做主路径；**保留**旧「下一节 + 确认框」那一套作**回退**——树不可用（容器缺失 / 没有节节点 / 认不出 `posCatalog_active`）时先等一个窗口期，仍不可用才回退。
2. **只向前**：候选 = 树上排在当前节点**之后**的第一个带计数节点；当前节点自己还有可播的未完成任务点就地播。不回头（手动跳章留下的空洞交回用户），也不做回环。
3. **候选判据是 `input.jobUnfinishCount` 存在**（不是「没有 `icon_Completed`」）——这样「只有资料附件 / 空内容」的节点直接不进候选，不必白跑一趟。
4. **安全网换成树交叉校验**：允许跳过当前节点的前提是树上它已无未完成计数；树上说有未完成时——「看到过未完成任务点但都是脚本播不了的」允许跳过（承 `0007`），「一个未完成任务点都没看到」**停下**（新停止原因 `treeUnfinishedNotFound`）。确认框那一套降级为回退路径专用。
5. **「等章节树就绪」单独一条倒计时**（新 `PENDING.TREE_NOT_READY`，动手类：`N 秒后改用「下一节」推进`），按仓库纪律补用例。
6. **文档**：新落 `docs/adr/0010`；树的三件套选择器与「不弹框 / 不刷新树」写进 `docs/sites`；就地改写本文里「`jobUnfinishCount` 只用来显示、不参与决策」与「否掉交叉校验」两句并标指到 `0010`；`CONTEXT.md` 不动。
7. **结束原因**：保留一条 `courseCompleted`，文案按树重写、不宣称成绩；跳过只剩播不了的任务点的节点这件事由现场倒计时交代，不在结束文案里追述。
8. **跳转的退避与失败判据**：新记忆 `jumpRequested`（同一目标只跳一次，与 `startRequestedKey` 同款）；失败判据是「当前节点有没有真的变成目标」——`UNREADY_TIMEOUT_MS` 内没变成就沿用 `mediaNotFound` 停下（文案并列这一档）。

10. **顺带补上 US9**：树可用时把「本节点未完成 N（含 PPT）」换成「后面还有 M 个任务点未完成（含 PPT）」（当前节点之后各节点计数之和）——这是这次改动白捡的信息，关掉了本文自第一轮起挂着的那条降级。
11. **验收档位**：用例全绿 + 真机只读确认「只跳一次就到 4.1」（到位立刻按「停止」），不为了看「播完 → 跳走」而真的播完一个任务点（那一段用的是既有逻辑）。
12. **提交**：分两次——文档先行（ADR + 站点事实 + spec + 工单），实现随后。工作区里那两个已 `git add` 的 `docs/usage/*.md` 留在暂存区不动。

**由此被翻转的既有白纸黑字**（都在原处标了指路，不静默改）：`0006` 的「`jobUnfinishCount` 只用来显示、不参与决策」与「安全网是平台那张确认框」（`0010` 的 Consequences 已记）；`0005` / `0007` 的「跳过 = 点下一节并代为确认」在树路径上不再发生（机制换成跳节点，授权问题随之消失）。
