# 推进 = 从章节树直接跳到下一个未完成节点（只向前）

`0006` 的 Consequences 里写着「`input.jobUnfinishCount` 只用来显示进度，不参与决策」；推进的方式一直是**点「下一节」**（`PCount.next`），一次只走一个节点。用户实测发现这在一种常见场面下是纯浪费：**打开的是开头的节点、但前面一大段早就做完了**，脚本会一个节点一个节点地走完那一段——每个节点都要一次局部刷新，还会在每个**已完成**的节点里 `play()` 一次它的媒体（实测日志里一串 `playingTime=0` 的上报）。

用户的要求：**只经过未完成的节点，检查未完成的节点里有没有可播的任务点**；以某课程为例，1.1–3.9 全已完成，从 1.1 打开就应该直接进 4.1。

三条**实现事实**（都实测于学习页，见 `docs/sites/xuexitong.md` § 章节树与跳节点）：

- **整棵章节树就在学习页的主文档里**（`#coursetree`，由 `studentstudycourselist` 铺满），每个「节」是 `div.posCatalog_select#cur<chapterId>`，当前节点额外带 `posCatalog_active`。节点上有两个**互斥**标记：已完成 = `span.icon_Completed`，未完成 = `input.jobUnfinishCount`（值 = 待完成数，含 PPT）；**只有资料附件或空内容的节点两个都没有**。
- **跳节点的入口就是站点自己的**：`span.posCatalog_name` 的 `onclick="getTeacherAjax(courseId, clazzid, chapterId)"`。实测它一次 `GET studentstudyAjax` 换掉 `#mainid`：**不整页重载**（`window` 全局与脚本实例都活着）、**跨章也不需要 `changeCapter`**、而且**不弹「还有任务点未完成」确认框**——`checkJob()` 只写在 `PCount.next` 里，`getTeacherAjax` 里没有。
- **树会被平台自己刷新，但时机不可控**（跳转本身只产生 `studentstudyAjax` + `validatejobcount`，后者只回 `"true"`；实测跳转之后会接着出现一次 `studentstudycourselist?chapterId=<目标节点>`）。所以**选目标不能假设树是新鲜的**：刚播完的节点在树上可能仍然写着未完成。

因此我们决定：**「推进」从「点邻节点的下一节」改成「从章节树跳到下一个未完成节点」，且只向前。**

- **候选判据是 `input.jobUnfinishCount` 存在**（＝平台自己说这个节点还有事没做），不是「没有 `icon_Completed`」。
- **只向前**：候选 = 树上排在**当前节点之后**的第一个带计数的节点（用 `posCatalog_active` 在节点列表里的下标定位当前节点）。当前节点自己还有可播的未完成任务点时就地播，不跳。
- **跳过当前节点的前提是树同意**（见 Consequences 第一条）。
- **树不可用**（容器缺失 / 一个节节点都没有 / 认不出 `posCatalog_active`）时先等一个窗口期，仍不可用就**回退到旧的「下一节 + 确认框」路径**——`ADVANCE` / `CONFIRM_ADVANCE` 与它们的文案、用例原样保留，只为这一档存在。

## Considered Options

- **从头幂等找（现在的哲学）**：放弃。用户手动跳到 5.1 而 4.1 还没做时，脚本会**回头**跳 4.1，等于跟用户抢控制权，也与 US23「手动跳章之后它依然能正确接上」相抵触。而且从头找要额外记一份「已排除节点」账本才不会被刚播完的节点反复选中（树是陈旧的），只向前的下标比较天然免疫这件事。
- **先向前、后面找不到了再回头**：放弃。它只在「用户手动跳过前面的节点」这一种场面下多救回一点进度，代价是脚本会在跑到末尾后**突然往回跳**——用户无从预期，也没法从状态条上看懂它为什么回头。
- **候选判据用「没有 `icon_Completed`」**：放弃。两者对「有任务点未完成」的节点结论一致，差别落在**只有资料附件或空内容**的节点上——这种节点两个标记都没有，用这条判据会把它当候选、白跑一趟并多跳一次。用 `jobUnfinishCount` 直接跳过它，正是 `0006`「资料附件不进计数」的延续。
- **不校验、直接向前跳**：放弃。确认框是**平台自己**在拦（`PCount.next` → `checkJob()` → `showCheckDiv`），它是 `0006` 那张安全网的全部依据；树跳转绕开了它，于是「适配层漏判」这件事就没人管了（站点改版换容器类名、某个真任务点漏了 `jobid`），表现为**静默跳过没看的视频**。改成用树上的计数做交叉校验，比确认框更强：计数是平台每次都给、不依赖脚本先做错某个动作。
- **把「已排除节点」持久化下来**（下次不再白跑那些只剩 PPT 的节点）：放弃。spec 的幂等设计明确「不保存任何跨页状态、不依赖 `localStorage`」，为一点重复走访换掉整条设计不划算。
- **彻底删掉「下一节 + 确认框」那一套**：放弃。`#coursetree` 的内容靠 ajax 铺，启动瞬间可能是空的；「树不可用」到底是「还没铺好」还是「这页根本没有树」在客户端分不干净。留一条已真机验收过的回退比删掉它便宜，决策核心里只是一次 `tree === null` 的分叉。

## Consequences

- **安全网换成树交叉校验**：允许跳过当前节点的前提是**树上当前节点已经没有未完成计数**。树上还写着有未完成时再分两种——扫遍全部卡片、**看到过**未完成任务点但都是脚本播不了的（PPT / 认不出类型）→ 允许跳过（承 `0007`）；扫遍全部卡片、**一个未完成任务点都没看到** → 停下，新停止原因 `treeUnfinishedNotFound`。`0006` 那张确认框在树路径上永远不会出现，它作为安全网的职责由这条接手；确认框那一套（`mediaIncompleteConfirm` / `dialogWithoutUnfinished` / `confirmAdvance`）降级为**回退路径专用**。
- **`input.jobUnfinishCount` 从「只用来显示」升级为「选目标的判据」**——推翻 `0006` 的 Consequences 那一句。它仍然是**含 PPT** 的数，所以「只剩脚本播不了的任务点」的节点照样是候选，脚本会跳过去看一眼才发现没可播的（这正是用户要的「检查未完成的节点里有没有可播的任务点」）。
- **已知代价（如实记）**：那种节点在平台上永远不会变成「已完成」，所以**每个 session 都要再白跑一趟**（一次跳转 + 一次卡片扫描）；不持久化账本（见 Considered Options）。另外脚本**只向前**——用户手动跳过后留下的空洞不会再被回头补上，这一步交给用户自己决定（与 `0002` 以来「不替用户改判」的立场一致）。
- **退休与新增**：新增动作 `JUMP_NODE`、观察值 `tree`、记忆 `jumpRequested`、等待 `PENDING.TREE_NOT_READY`、停止原因 `treeUnfinishedNotFound`。`ADVANCE` / `CONFIRM_ADVANCE` / `ADVANCE_REPEAT_GUARD_MS` **不删**（回退路径仍在用）。跳转的失败判据不是「点了没反应」，而是「当前节点有没有真的变成目标」——沿用 `UNREADY_TIMEOUT_MS`（30 秒），`mediaNotFound` 的文案并列这一档。
- **`courseCompleted` 的语义跟着变**：从「页面上没有『下一节』入口」变成「当前节点之后没有带未完成计数的节点了」。它同时吞掉两种落地方式——后面真没有了、以及后面的未完成节点全是脚本播不了的（被逐个跳过后落到同一处）；文案照 `0008` 那轮的口径**不宣称成绩**。
- **状态条顺带补上 US9**：树可用时把「本节点未完成 N（含 PPT）」换成「后面还有 M 个任务点未完成（含 PPT）」（当前节点之后各节点计数之和）。这是这次改动白捡的信息，关掉了 spec 自第一轮起就挂着的那条降级。
- **`#coursetree` 的可用性成为一条新的运行时前提**：站点若把它挪走或改结构，脚本会先等 `TREE_READY_GRACE_MS` 再退回旧的推进路径——不会因此停下，只是变慢。这条前提写在 `docs/sites/xuexitong.md` 里。
